# LCI-01 — Lighthouse CI для Core Web Vitals

**Приоритет:** Medium · **Статус:** done 2026-11-12 · **Создан:** 2026-11-11
**Основание:** BACKLOG.md Medium («Проверить результаты в PSI»),
SEO-PLAN.md §8.1 («Core Web Vitals — не измерено»)

## Зачем

CWV стоят в KPI как «не измерено», при этом в SPEC и SEO-PLAN уже сделаны
две перф-правки (CLS блога через `width/height/loading/decoding`,
`Cache-Control` на `/blog/assets/`) — и ни одна не была проверена
замером. Нужен повторяемый прогон, который ловит регрессию до деплоя,
а не после жалобы пользователя.

## Что сделать

1. `lighthouserc.json` (или `lighthouserc.js`) в корне репозитория с
   бюджетами по трём метрикам и `assertions` на них.
2. Workflow `.github/workflows/lighthouse-ci.yml`, запускаемый вручную
   (`workflow_dispatch`) и по расписанию раз в неделю — **не на каждый
   пуш**, Lighthouse жжёт минуты runner'а.
3. Отчёт сохранять артефактом (`actions/upload-artifact`): HTML-отчёт
   нужен основателю, а не только CI-лог.

### Бюджеты (стартовые, уточнить по факту первого замера)

| Метрика | Порог «Good» | Порог падения |
| --- | --- | --- |
| LCP | ≤ 2.5 с | > 4.0 с |
| CLS | ≤ 0.1 | > 0.25 |
| INP/TBT | ≤ 200 мс | > 600 мс |

Первый прогон — **только замер**, без жёстких `error`-assertion: иначе
воркфлоу сразу станет красным из-за неизвестного базлайна. Пороги
фиксируются после первого отчёта.

### Что мерить

Минимум три URL: `/`, `/es/`, `/blog/<самая свежая статья>/`. Одной
главной недостаточно: `/es/` и блог генерируются из другого пайплайна и
деградируют отдельно.

## Acceptance

```bash
node --check bin/build-blog.mjs   # существующие чеки не сломаны
# ручной прогон Lighthouse по трём URL даёт численные LCP/CLS/INP,
# а не «не измерено»
```

В отчёте — три замера в цифрах и HTML-артефакт. KPI в SEO-PLAN.md §8.1
обновляется этими цифрами.

## Ограничения

- Не менять `index.html`, `es/index.html`, `bin/build-es.mjs` ради
  метрик: сначала замер, потом — отдельный бриф на правки.
- В репозитории сейчас **ноль зависимостей** и нет `package.json`.
  Если Lighthouse требует зависимостей, это отход от принципа
  «no build steps» — сначала записать решение в DECISIONS.md с причиной,
  потом добавлять. Предпочтительнее CI-only установка, которая не
  касается рабочего дерева.
- Воркфлоу не должен запускаться на каждый пуш.

## Если Заблокировано

Если Lighthouse требует Chrome в CI и runner его не тянет — пробовать
`--chrome-flags="--no-sandbox"`. Если не поднимается, вернуть блокером
с точной ошибкой, не подменяя замер скриншотом PSI из браузера.
